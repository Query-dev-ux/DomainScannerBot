# DomainScannerBot

Telegram-бот для мониторинга репутации доменов. Периодически выгружает домены из
PWA-платформ (PWApartners, SkakApp), проверяет их в security-сервисах, хранит историю
результатов и присылает уведомление в группу, если статус домена ухудшился.

## Как это работает

```
PWApartners ─┐
              ├─sync──▶  PostgreSQL  ◀──scan── Checkers (DNSBL, GSB, Facebook)
SkakApp ──────┘              │
                             ▼
                  APScheduler (внутри бота)
                             │
                             ▼
                Telegram: алерт в группу + команды
```

- **Sync** (`SYNC_INTERVAL_MINUTES`) — тянет списки доменов из каждого подключённого
  источника, добавляет новые, обновляет их статус в платформе.
- **Scan** (`SCAN_INTERVAL_MINUTES`) — проверяет все домены. Проверки выполняются
  параллельно (`SCAN_CONCURRENCY`), вердикт агрегируется по худшему результату.
- **Alert** — сообщение в `ALERT_CHAT_ID` отправляется только при **изменении**
  вердикта на `подозрительно` или `зашкварен`.

### Источники доменов

Источник включается, как только в `.env` заполнены его ключи; нужен хотя бы один.

| Источник | Доступ | Откуда берутся домены |
|---|---|---|
| PWApartners | `PWA_API_KEY`, `PWA_TEAM_UUID`, `PWA_TEAMATE_UUID` | `GET /dash_api/domains/list`; владелец — по `teamate_uuid` через `GET /dash_api/team/list` |
| SkakApp | `SKAKAPP_LOGIN` + `SKAKAPP_PASSWORD` (Basic-auth; API-ключ SkakApp не нужен) | `POST /pwa/list`: `domains[]` (с признаком бана) и домены сплитов; владелец — `createdUsername` |

**Проверяется каждый домен, который отдаёт источник.** Статус платформы не решает,
проверять домен или нет, но сам по себе является сигналом: бан в PWApartners — это уже
плохой домен, см. checker `source_status`. Домен, пропавший из источника, перестаёт
проверяться; вернётся — снова начнёт проверяться.

У каждого домена в базе есть владелец (`domains.source`), и синк источника трогает только
свои домены. Если домен приходит из двух источников, им владеет первый; если владелец его
удалил, а второй источник по-прежнему отдаёт — домен переходит ко второму и продолжает
проверяться. Домен, добавленный вручную через `/check`, забирает первый источник, который
его вернёт. Источники синхронизируются независимо: если один упал, второй всё равно
обновится, а в группу придёт сообщение, какой именно не ответил.

Новый источник = класс с `source`, `title` и `async def fetch_domains() -> list[SourceDomain]`
в `src/domain_scanner/sources/`, добавленный в `build_providers()`.

### Автоматический режим

Оба задания крутит APScheduler внутри процесса бота — отдельный воркер или cron не нужен.

| | Как часто |
|---|---|
| Подгрузка доменов из источников | раз в `SYNC_INTERVAL_MINUTES` (60 мин), первый раз через 30 сек после старта |
| Проверка **всех** доменов | раз в `SCAN_INTERVAL_MINUTES` (60 мин), первый раз через 2 мин после старта |

Проверки идут параллельно (`SCAN_CONCURRENCY`); ~400 доменов проходят за несколько
минут. Если прогон вдруг займёт дольше интервала, второй параллельно не запустится —
следующий начнётся после него.

### Вердикты

| Вердикт | Значение |
|---|---|
| `clean` | чисто во всех проверках |
| `suspicious` | домен не резолвится, просрочен в источнике, краулер FB не прочитал страницу |
| `flagged` | забанен в источнике / найден в блоклистах / GSB / заблокирован в Facebook |
| `error` | все проверки завершились ошибкой |

## Проверки (checkers)

| Checker | Ключ | Что покрывает |
|---|---|---|
| `source_status` | не нужен | статус домена в платформе: бан в PWApartners (`status 9`) или в SkakApp (`is_baned_register`) → `зашкварен`; просроченный в PWApartners → `подозрительно` |
| `dns_rbl` | не нужен | резолв домена + Spamhaus DBL / SURBL |
| `google_safe_browsing` | `GSB_API_KEY` | malware / phishing / unwanted software |
| `facebook` | `FB_APP_ID` + `FB_APP_SECRET` | блокировка ссылки внутри Facebook. Не больше `FB_HOURLY_LIMIT` доменов в час: каждая проверка заставляет FB сходить на страницу, и Graph API это жёстко лимитирует |

### Как работает проверка Facebook

Официального API «заблокирован ли домен» нет. Чекер использует **Graph API URL node**
со `scrape=true` (`POST /v21.0/?id=https://<домен>/&scrape=true`) — тот же вызов, что
делает [Sharing Debugger](https://developers.facebook.com/tools/debug/). Аутентификация —
app access token (`{app_id}|{app_secret}`), логин пользователя не нужен.

`scrape=true` здесь принципиален: без него Graph отдаёт только то, что у Facebook уже
закэшировано, и на незнакомый домен отвечает нулями без ошибки — мёртвый домен выглядит
как здоровый. Со `scrape=true` Facebook реально идёт на страницу.

| Ответ Graph API | Вердикт |
|---|---|
| есть `title` / `description` / `image` — страница прочитана | `clean` |
| ошибка с маркером блокировки (`Community Standards`, `not allowed`, `unsafe`…) | `flagged` |
| только `url` / `type` / `updated_time` — FB не смог прочитать страницу | `suspicious` |
| transient / rate limit / кривые креды / незнакомая ошибка | `error` (алерт не шлётся) |

Полный ответ Graph API всегда сохраняется в `scan_checks.raw` — по накопленным данным
списки маркеров в [checkers/facebook.py](src/domain_scanner/checkers/facebook.py)
можно уточнять. Незнакомые ошибки пишутся в лог как `facebook.unknown_error`.

Новый checker = класс с атрибутом `name` и методом `async def check(domain) -> CheckOutcome`,
добавленный в `build_checkers()` (`src/domain_scanner/checkers/__init__.py`).

## Запуск

```bash
cp .env.example .env      # заполнить токены и ключи
docker compose up -d --build
```

`docker compose` поднимает Postgres, прогоняет миграции (`migrate`) и запускает `bot`.

Развёртывание на сервере (в т.ч. рядом с другими контейнерами, переиспользование
существующего Postgres, бэкапы, обновление) — [DEPLOY.md](DEPLOY.md).

### Локально без Docker

```bash
python -m venv .venv && . .venv/Scripts/activate   # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
# поднять Postgres где-то локально, прописать POSTGRES_* в .env
alembic upgrade head
python -m domain_scanner
```

## Команды бота

| Команда | Действие |
|---|---|
| `/status` | сколько доменов и сколько из них в каждом вердикте |
| `/list` | проблемные домены: сначала «Новые», затем «Не отслеживаемые», внутри — по источнику, с тегами причины («Заблокирован в PWA сервисе», «Заблокирован в FB», «Под подозрением») |
| `/list clean` · `/list flagged` … | домены с конкретным вердиктом |
| `/check <домен>` | проверить домен сейчас (если его нет в базе — добавится) |
| `/scan_now` | проверить все домены сейчас |
| `/sync_now` | подтянуть домены из всех источников |

Под алертами и карточками `/check` — кнопки **Перепроверить** (новая карточка ответом,
исходный алерт остаётся в истории) и **Не отслеживать** / **Отслеживать**. Под `/list` —
кнопка **Не отслеживать новые (N)**: снимает с проверки всё из раздела «Новые» разом и
тут же перерисовывает список. Если ручная
проверка обнаружила ухудшение, алерт всё равно уходит в группу.

Карточка домена — это заголовок с причиной («Домен под подозрением», «Домен
заблокирован в PWA сервисе», «Домен заблокирован в FB»), сам домен, его источник и
владелец. В `/list` домены сгруппированы по источнику, а внутри — по владельцу.
Логины платформ (у PWApartners это e-mail) можно заменить на понятные имена через
`OWNER_ALIASES` в `.env`: `почта=Имя`, пары через запятую.
Все тексты бота собраны в [bot/render.py](src/domain_scanner/bot/render.py); стиль
минималистичный — без эмодзи и без лишней информации.

Доступ ограничен списком `ADMIN_IDS` (если пуст — команды доступны всем).

## Разработка

```bash
pytest
ruff check src tests
alembic revision --autogenerate -m "..."   # новая миграция
alembic check                               # модели и миграции не разъехались
```

Тесты синхронизации (`tests/test_sync_db.py`) работают с настоящим PostgreSQL и
пропускаются, если не задан `TEST_DATABASE_URL` — укажите одноразовую базу с
применёнными миграциями, таблицы в ней очищаются перед каждым тестом:

```bash
TEST_DATABASE_URL=postgresql+asyncpg://user:pass@127.0.0.1:5432/domain_scanner_test pytest
```

Стек: Python 3.12, aiogram 3.x, SQLAlchemy 2 (async) + asyncpg, Alembic,
APScheduler, aiohttp, pydantic-settings.
